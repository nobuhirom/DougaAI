# 全体計画 — 12工程をすべて作る

作成日: 2026-09-15
前提: [01_調査メモ.md](01_調査メモ.md) / [04_要件定義.md](04_要件定義.md)

[04_要件定義.md](04_要件定義.md) はフェーズ1（台本 JSON → 動画）だけを定義していた。
事例A の12工程すべてを作る方針が決まったため、全体像をここに置く。

```
ネタ決め → 企画メモ → 調査 → 台本 → レビュー → ビジュアル → 音声
        → サムネイル → 組み立て → ショート → 多言語化 → 投稿
```

---

## 1. 誰が実行するか

工程を3種類に分ける。**この区別が設計の骨格**になる。

| 分類 | 実行者 | 性質 |
| --- | --- | --- |
| **人間** | 手で書く・選ぶ | 起点の判断と、最終的な良し悪しの判断 |
| **エージェント** | コーディングエージェント（Claude Code 等） | 文章・構成・翻訳の生成。プロンプトと成果物スキーマで縛る |
| **機械** | 決定的なコード | 検証・計算・レンダリング。同じ入力から必ず同じ出力 |

### AI 工程を API 呼び出しにしない理由

[04_要件定義.md](04_要件定義.md) N6 と P1 が、従量課金の API に依存しないことを求めている。
LLM の API を Node から叩くと、1本作るごとに課金が乗り「何本作っても定額」が崩れる。

事例A も「コーディングエージェントのサブスク範囲で完結し、何本作っても定額」と明言している。

そこで **AI 工程は「ファイルを読んでファイルを書く手順」として定義する**。

- パイプライン側が持つも: 成果物のスキーマ、プロンプト、検証、次に何をすべきかの提示
- エージェントが行うこと: プロンプトに従って入力成果物を読み、出力成果物を書く

パイプラインは LLM を呼ばない。呼ぶのはエージェント自身が動くときだけ。
結果として、**どのエージェントを使うかをパイプラインが知らなくてよい**という副作用もある。

---

## 2. 成果物とその流れ

各工程は**ファイルを入力にファイルを出力する**。途中の状態をメモリに持たない。
中断・再開・部分的なやり直しが効く。

```
projects/<id>/
├── idea.json        ネタ決め      人間 → 起点
├── plan.md          企画メモ      エージェント（人間が書き直す）
├── research.md      調査          エージェント（人間が確認）
├── script.json      台本          エージェント（人間が書き直す）★フェーズ1 で確定済み
├── thumbnail/       サムネイル    エージェント + 人間が選ぶ
├── shorts.json      ショート      エージェント（台本から切り出す）
└── i18n/<lang>.json 多言語        エージェント（台本から翻訳）
```

| # | 工程 | 入力 | 出力 | 実行者 | 検証 |
| --- | --- | --- | --- | --- | --- |
| 1 | ネタ決め | — | `idea.json` | 人間 | スキーマ |
| 2 | 企画メモ | `idea.json` | `plan.md` | エージェント | 構成の必須項目 |
| 3 | 調査 | `plan.md` | `research.md` | エージェント | 出典の有無 |
| 4 | 台本 | `plan.md` `research.md` | `script.json` | エージェント | **機械的チェック8種** |
| 5 | レビュー | `script.json` | `ai-review-logs.jsonl` | エージェント | 指摘の深刻度 |
| 6 | ビジュアル | `script.json` | `script.json`（`visual` を埋める） | エージェント | 型の妥当性 |
| 7 | 音声 | `script.json` | `build/<id>/` | **機械** | 尺の異常 |
| 8 | サムネイル | `plan.md` `script.json` | `thumbnail/` | エージェント + 人間 | 文言は2文まで |
| 9 | 組み立て | `manifest.json` | `out/<id>.mp4` | **機械** | 決定性 |
| 10 | ショート | `script.json` | `shorts.json` | エージェント | 尺・冒頭2秒 |
| 11 | 多言語化 | `script.json` | `i18n/<lang>.json` | エージェント | id の対応・文の途中切れ |
| 12 | 投稿 | `out/` `thumbnail/` | — | 人間 | — |

**7 と 9 だけが機械**で、ここはフェーズ1 で実装済み。残りはエージェントと人間の工程になる。

## 3. 人間を残す場所

事例A が全自動にしていない工程をそのまま踏襲する（[01_調査メモ.md](01_調査メモ.md)）。

| 工程 | 人間の役割 | なぜ自動化しないか |
| --- | --- | --- |
| ネタ決め | 気になることを列挙する | **起点は必ず人間**。AI が勝手にネタを決めても、作りたいものにならない |
| 台本 | 構成案とセリフを納得いくまで書き直す | 動画の質がここで決まる |
| ビジュアルの型 | 型を作り込む段階で目視確認 | 字幕の重なり・見切れは目で見ないと分からない |
| サムネイル | 背景を複数案から選ぶ / 文言を決める | 自動生成は「ごちゃごちゃ・色が多い・視線が迷う」になりがち |

**用途ごとに関与度を変える**（[02_論点整理.md](02_論点整理.md) Q5-1 の決定）。

| 用途 | 人間の関与 |
| --- | --- |
| 解説動画（公開） | 上の4工程すべてで人間が入る |
| 自分専用の学習動画 | ネタ決めのみ。あとは通す |
| 資料の動画化 | ネタ決めの代わりに資料を渡す。台本だけ確認する |

## 4. Web UI の役割

事例A は Remotion 標準の編集 UI を使わず、独自の Web UI でプレビュー・調整している。

**UI がやること**: 見る・選ぶ・直す

- ネタの書き捨てと一覧
- 企画メモ・台本の閲覧と編集
- 検証結果をその場で赤く出す（字幕のはみ出し等）
- プレビュー再生（`@remotion/player`）
- サムネイル候補から1枚選ぶ

**UI がやらないこと**: AI を呼ぶこと

生成はエージェントが端末側で行う。UI から LLM を叩くと、結局 API 課金に戻る。
UI は生成された成果物を見て直す場所に徹する。

## 5. 改善ループ

事例A の中核。**本数を重ねて初めて効く**ので、最初からログを取る。

| ファイル | 何を記録するか | いつから |
| --- | --- | --- |
| `logs/modifications.jsonl` | 人間が何をどう直したか | フェーズ1 から |
| `logs/ai-review-logs.jsonl` | AI レビューの指摘・深刻度・何回目で通ったか | フェーズ2 から |

溜まったログをプロンプトとレビュー観点に還元する。
**同じ修正を人間が二度やらないよう、仕組み自体を直す。**

---

## 6. 実装の順序

| フェーズ | 内容 | 工程 | 状態 |
| --- | --- | --- | --- |
| **1** | 台本 JSON → 動画 | 7, 9 | **完了**（[04_要件定義.md](04_要件定義.md) 11章に検証結果） |
| **2** | ネタ → 企画 → 調査 → 台本 | 1〜4 | 次 |
| **3** | レビューと改善ループ | 5, 6 | |
| **4** | Web UI | 全工程の閲覧・編集 | |
| **5** | サムネイル | 8 | |
| **6** | ショート・多言語化 | 10, 11 | |

**この順序を守る理由**: 後ろの工程は前の工程の成果物を入力にする。
レビュー（5）は台本（4）がないと何も評価できない。UI（4）は表示するものが
ないと形が決まらない。フェーズ1 を先に作ったのと同じ理屈で、
**検証できないものを先に作らない**。

## 7. コストの見通し

| 項目 | 費用 |
| --- | --- |
| Remotion | 無償（個人利用） |
| Irodori TTS | 無償（MIT・ローカル） |
| AI 工程 | コーディングエージェントのサブスク内 |
| レンダリング | ローカル（電気代のみ） |

これは P1 から一貫した設計方針で、12工程に広げても崩さない。
