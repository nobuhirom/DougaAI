## 1. このシステムは何か

**構造化データ（台本 JSON）を単一の正として、解説動画を決定的にレンダリングするシステム。**

編集ソフトを使わず、動画生成 AI も使わない。台本 JSON を入力すると MP4 が出る。同じ JSON からは常に同じ動画が出る。

### 3つの用途と優先順位

| 優先 | 用途 | 性質 | 扱い |
| --- | --- | --- | --- |
| **1** | 解説動画（キャラ掛け合い＋スライド） | 公開・量産 | **最初に作る**。これが本体 |
| 2 | 自分専用の学習動画 | 非公開・量産 | 同じパイプラインの簡易プリセットで賄う |
| 3 | 資料の動画化 | 入力が定型なら量産 | 「資料 → 台本 JSON」の変換を足すだけにする |

用途1のパイプラインが用途2・3を含む形で設計する。**別系統を作らない**。

## 2. スコープ

### フェーズ1（MVP）— 「JSON を書いたら動画が1本出る」

これが完成の第一定義。

| 含む | 含まない |
| --- | --- |
| 台本 JSON のスキーマ定義と検証 | 台本の AI 自動生成 |
| Irodori TTS による音声生成 + キャッシュ | サムネイル生成 |
| 音声長からの尺決定 | ショート動画の切り出し |
| キャラクター2人の立ち絵・表情・口パク | 多言語化 |
| 字幕（日本語の改行・禁則処理つき） | Web UI |
| ビジュアル6型 | BGM の自動選曲 |
| BGM・効果音の配置 | クラウドレンダリング |
| レンダー前の機械的チェック | |
| CLI（`validate` / `build` / `render` / `preview`） | |

### フェーズ2 — 台本を AI に書かせる

MVP が動いてから着手する。**レンダリングできないものは自動生成しても検証できない**ため、この順序は動かさない。

- 企画メモ → 調査 → 台本 → レビューのエージェント分割
- 修正ログ（`modifications.jsonl` / `ai-review-logs.jsonl`）を使った改善ループ
- ビジュアルの型選択を AI に任せる

### フェーズ3以降 — 公開運用

サムネイル、ショート、多言語化、投稿。`02_論点整理.md` Q5-3 の通り**当面スコープ外**。

ただし**データモデルだけは最初から多言語・ショートに耐える形にする**（`id` の安定性、テキストの一元管理）。後から構造を変えるのはコストが高いため。

## 3. データモデル

### 3.1 二層に分ける

事例A は1枚の JSON に `durationInFrames` まで載せていたが、本システムでは**人間/AI が書くもの**と**ビルドが生成するもの**を分離する。

| 層 | ファイル | 誰が書くか | 再生成 |
| --- | --- | --- | --- |
| **台本**（source） | `projects/<id>/script.json` | 人間 / AI | しない。これが正 |
| **マニフェスト**（derived） | `build/<id>/manifest.json` | ビルド | 常に再生成可能。**git 管理しない** |

理由: 音声長やフレーム数を台本に書き戻すと、台本が「編集していいファイル」でなくなる。差分レビューもノイズだらけになる。派生物は派生物として隔離する。

### 3.2 台本スキーマ

```jsonc
{
  "meta": {
    "id": "remotion-intro",          // プロジェクト識別子
    "title": "動画タイトル",
    "fps": 30,
    "width": 1920,
    "height": 1080,
    "characters": ["kaede", "tsumugi"]  // 登場人物（characters/ の定義を参照）
  },
  "sections": [
    {
      "type": "introduction",        // introduction | main | summary | outro
      "name": "導入",
      "lines": [
        {
          "id": "s0_intro_001",      // 安定識別子。once assigned, never reused
          "character": "kaede",
          "text": "セリフ本文。字幕にそのまま出る",
          "emotion": "explain",
          "visual": { "type": "bullets", "title": "…", "items": ["…"] },
          "bgm": "calm-01"           // 省略時は直前を継続
        }
      ]
    }
  ]
}
```

### 3.3 論点の決定

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| **Q2-1** `id` の命名 | `s{セクション番号}_{type}_{3桁連番}` 例: `s3_main_004` | 事例A を踏襲。人間が読んで位置が分かる。**一度振ったら再利用しない**（翻訳の書き戻し・ショート指定の参照先になるため） |
| **Q2-2** `visual` の形 | **オブジェクトに統一**（`type` を判別子とする discriminated union） | 文字列とオブジェクトの混在は型が効かない。パラメータを持たない型でも `{"type":"none"}` と書く |
| **Q2-3** キャラクター | **2人の掛け合い**。ただし1人でも成立する構造 | 用途2（学習動画）はナレーション1人で十分。`characters` を1要素にすれば動く |
| **Q2-4** `emotion` の語彙 | **6語**から始める: `normal` / `explain` / `happy` / `surprised` / `thinking` / `trouble` | 表情差分の作成コストと釣り合う数。Irodori TTS の絵文字制御にもマップする（3.4） |
| **Q2-5** セクション `type` | `introduction` / `main` / `summary` / `outro` の4種 | OP・アイキャッチ・ED などの定型パーツは**セクション種別から自動挿入**する。台本に書かせない |

### 3.4 emotion の二重の役割

`emotion` は**表情スプライトの選択**と **TTS の感情制御**の両方を駆動する。Irodori TTS は絵文字埋め込みで感情を制御するため、語彙から絵文字へのマップを持つ。

| emotion | 表情スプライト | TTS 絵文字 |
| --- | --- | --- |
| `normal` | `normal.png` | （付与しない） |
| `explain` | `explain.png` | （付与しない） |
| `happy` | `happy.png` | 😊 |
| `surprised` | `surprised.png` | 😮 |
| `thinking` | `thinking.png` | 🤔 |
| `trouble` | `trouble.png` | 😓 |

**字幕には絵文字を出さない**。TTS へ渡すテキストにのみ付与する。台本の `text` は字幕にそのまま出る文字列であり続ける。

### 3.5 ビジュアルの型（Q3-1 / Q3-2）

6型から始める。事例A は9型＋レイアウトパターンだが、**型は必要になってから足す**方が、使われない型の保守コストを避けられる。

| type | 用途 | 主なパラメータ |
| --- | --- | --- |
| `none` | キャラの掛け合いのみ | — |
| `title` | セクション見出し・アイキャッチ | `text`, `subtitle?` |
| `bullets` | 箇条書きスライド | `title`, `items[]`, `highlight?` |
| `code` | コード表示 | `language`, `code`, `highlightLines?` |
| `compare` | 2カラム比較 | `left{title,items}`, `right{title,items}` |
| `image` | 画像・スクリーンショット | `src`, `caption?`, `fit?` |

**用途3（資料の動画化）での図表の扱い**: 元資料の図表は `image` 型で画像として貼る。型への変換は行わない。変換精度が読めず、間違った図を自信満々に出すリスクが割に合わない。

**後で足す候補**: `terminal` / `stats` / `quote` / `diff` / `table`。

### 3.6 キャラクター定義

台本とは別に `characters/<id>/` で定義する。台本から名前で参照する。

```
characters/kaede/
├── character.json      # 表示名・色・字幕スタイル・TTS 設定
├── persona.md          # 役割・性格・話し方（フェーズ2の AI レビュー照合用）
├── expressions/        # normal.png / explain.png / … （6種）
└── voice/
    ├── reference.wav   # Irodori TTS の参照音声
    └── caption.txt     # VoiceDesign 用の声質記述
```

`persona.md` は事例A の `sharina.md` / `renka.md` に相当する。**フェーズ1では使わないが、置き場所だけ用意する**（フェーズ2 のキャラブレ検出で使う）。

## 4. 音声（TTS）

### 4.1 方式

Irodori TTS をローカル実行（Python + uv、MPS/CPU）。[Irodori-TTS-Server](https://github.com/Aratako/Irodori-TTS-Server)（OpenAI TTS 互換 API）を立てて HTTP で叩く。

CLI 直叩きではなくサーバー経由にする理由: **1セリフごとにモデルをロードし直すのを避ける**ため。10分動画で100セリフ規模になると、ロード時間が支配的になる。

### 4.2 音声キャッシュ（重要）

台本を1行直すたびに全セリフを再生成するのは現実的でない。**セリフ単位でキャッシュする**。

```
キャッシュキー = sha256(text + emotion + character + speed + refEmbedHash + modelVersion)
```

- 保存先: `build/<id>/audio/<キー>.wav`
- 台本の1行を直したら、その行だけ再生成される
- キーにモデルバージョンを含めるため、TTS 更新時は自動で全再生成される

### 4.3 尺の決定（Q4-4）

**音声長を基準に duration を決める。** 先に音声を作り、その長さで尺が決まる。

```
1. 各セリフの WAV を生成（またはキャッシュから取得）
2. ffprobe で長さを取得
3. durationInFrames = ceil(秒 * fps) + パディング
4. 全セリフの合計 + 定型パーツ = 動画全体の durationInFrames
```

Remotion 側では `calculateMetadata` で総尺を確定し、`<Series>` に各セリフを並べる。開始フレームの積算は `<Series>` が行う。

**パディング**: セリフ間に既定 6 フレーム（0.2秒）の間を入れる。詰まって聞こえるのを防ぐ。台本側で `pauseAfter` により上書きできる。

### 4.4 Q4-2 / Q4-3 の決定

| 論点 | 決定 |
| --- | --- |
| **Q4-2** 声質の固定 | **必要**。`characters/<id>/voice/reference.wav` と `--ref-embed` の埋め込みを固定して使い回す |
| **Q4-3** 学習動画にも音声が要るか | **要る**。同じパイプラインに載せる。ただし**画質と表現を落とすプリセット**（`--preset draft`）を用意し、レンダリング時間を削る |

Q4-3 で音声を捨てれば量産コストは下がるが、**パイプラインが2系統に割れる**代償の方が大きい。品質ではなく所要時間で差をつける。

### 4.5 読みの制御

Irodori TTS には読み指定の明示的手段が見当たらない。運用で吸収する。

- 固有名詞・技術用語は**台本の `text` にカタカナで書く**（例: 「Remotion」→「リモーション」）
- ただし**字幕には原綴りを出したい**場合があるため、`reading` フィールドで TTS 用の読みだけを上書きできるようにする

```jsonc
{ "text": "Remotion を使います", "reading": "リモーション を使います" }
```

`reading` 省略時は `text` をそのまま TTS に渡す。

## 5. 字幕

### 5.1 方針

**1セリフ = 1字幕**。セリフの音声が鳴っている間、その `text` を丸ごと表示する。

Irodori TTS が単語タイムスタンプを返さないため、カラオケ字幕（単語ごとのハイライト）は初版では実装しない。必要になったら HyperFrames `transcribe` でアライメントを取る（[03_方式決定.md](03_方式決定.md) 決定2）。

### 5.2 日本語の改行・禁則処理

Remotion は日本語の改行に公式対応していないため**自前実装する**。事例A の方式を出発点にする。

| 項目 | 値 |
| --- | --- |
| 1行の最大幅 | `30.93em`（事例A の実測値を初期値とし、実装後に調整） |
| 最大行数 | 2行 |
| 幅の見積もり | 全角 1.0em / 半角 0.55em |

**禁則処理**:
- 行頭禁則: `、。，．・？！」』）】〉》〕｝ぁぃぅぇぉっゃゅょゎァィゥェォッャュョヮーヽヾ々`
- 行末禁則: `「『（【〈《〔｛`
- 分離禁止: 数字と単位、連続する英数字

**はみ出しは機械的に検出してレンダー前に落とす**（7章）。折り返せずに3行になる、または1行が最大幅を超えるセリフは台本のミスとして扱う。

### 5.3 フォント

**システムフォント名に依存しない。** フォントファイルを `assets/fonts/` に同梱し、`@font-face` で読み込む。

HyperFrames の調査で「レンダリング環境にはヒラギノ・游ゴシック・Noto Sans CJK が存在せず、指定すると無言で汎用フォントにフォールバックする」という制約が判明した。Remotion はローカル Chrome を使うため手元では動いてしまうが、**環境を変えた瞬間に壊れる**。先回りして同梱方式にする。

採用フォント: **Noto Sans JP**（SIL Open Font License 1.1、再配布可）。

## 6. レンダリング

| 項目 | 値 |
| --- | --- |
| 解像度 | 1920×1080（16:9） |
| fps | 30 |
| コーデック | H.264 |
| 出力 | `out/<id>.mp4` |
| 想定尺 | 5〜10分（Q1-2） |

### プリセット

| preset | 用途 | 設定 |
| --- | --- | --- |
| `draft` | 確認用・学習動画 | `--scale 0.5`、JPEG フレーム、低ビットレート |
| `final` | 公開用 | フル解像度 |

`--concurrency` は `npx remotion benchmark` で実測して決める（公式に数値の記載がないため）。実行環境は Apple M5 / 10コア / 24GB。

## 7. 機械的チェック（P5）

**AI レビューより手前に置く。** レンダリング前に落とせるものは全部落とす。

| # | チェック | 落とす条件 |
| --- | --- | --- |
| 1 | スキーマ検証（zod） | 型・必須フィールド・enum 違反 |
| 2 | `id` の一意性 | 重複、命名規則違反 |
| 3 | 字幕のはみ出し | 2行に収まらない、1行が最大幅超過 |
| 4 | アセット参照 | `image.src` / `bgm` / 表情スプライトの実在確認 |
| 5 | キャラクター参照 | `meta.characters` に無いキャラが `line.character` に出現 |
| 6 | 空テキスト | `text` が空、または空白のみ |
| 7 | 音声欠落 | マニフェスト生成後、全セリフに WAV が存在するか |
| 8 | 尺の異常 | 1セリフが 30 秒超（TTS の暴走を検知） |

`douga validate` で全件実行し、1件でも違反があればビルドを止める。

## 9. 非機能要件

| # | 要件 | 理由 |
| --- | --- | --- |
| N1 | **決定性** — 同じ台本からは同じ動画が出る。CSS アニメーション・`Math.random()`・`Date.now()` を使わない（P2） | 再現性がないと差分検証ができない |
| N2 | **増分ビルド** — 台本の1行を直したら、その行の音声だけ再生成する | 1行の修正に全音声の再生成を伴うと反復できない |
| N3 | **派生物を git に入れない** — `build/` `out/` `*.wav` `*.mp4` は無視 | リポジトリの肥大化を防ぐ |
| N4 | **アセットは同梱** — フォント・BGM はシステム環境に依存しない | 環境差でサイレントに壊れるのを防ぐ |
| N5 | **失敗は止める** — 警告ではなくエラーにする。サイレント失敗を作らない | [03_方式決定.md](03_方式決定.md) の基盤選定理由そのもの |
| N6 | **ランニングコストゼロ** — 従量課金の API に依存しない（P1） | 「何本作っても定額」 |

## 11. 完成の定義

### フェーズ1 の完成条件

1. `projects/sample/script.json` から `out/sample.mp4` が生成される
2. 生成された動画で以下が確認できる
   - キャラクター2人が話者に応じて切り替わり、`emotion` に応じて表情が変わる
   - 口が音声に合わせて動く
   - 字幕が2行以内に正しく折り返され、禁則処理が効いている
   - ビジュアル6型がすべて表示される
   - BGM が鳴り、セリフが聞き取れる音量バランスになっている
3. `douga validate` が8種のチェックを実行し、違反を検出して停止する
4. 台本を1行変更して再ビルドすると、その行の音声だけが再生成される
5. 同じ台本から2回レンダリングして、バイト列が一致する（N1 の検証）
